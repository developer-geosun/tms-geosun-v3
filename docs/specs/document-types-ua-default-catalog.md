# Довідник видів документів UA: склад за замовчуванням

## Статус
- **Реализация:** реализовано (backend + Angular + Flyway `V39`)
- **Роль:** источник истины по UA-seed (UUID `c2000000-…`)
- **Клиент:** Angular + Java
- **Остаток:** нет. Самостійний документ: не посилається на інші специфікації і не змінює їх
- **Реестр:** [README.md](README.md)

## Мета
- Очистити таблицю `document_types` від усіх наявних рядків (seed і записи, створені вручну).
- Заповнити довідник **п’ятьма** видами документів України з фіксованими UUID, назвами, описом сторінок скана і набором полів.
- У кожного поля з’являється прапорець **`required`**. Поля з `required: true` — ті, що система бере в роботу; користувач їх **підтверджує**. Порожнє обов’язкове поле не приймається.
- `planned_scan_pages` зберігає **JSON-масив сторінок** (ключ + легенди en/ua/ru), а не число.
- Колонка **`comment`**: вільний текст; у seed — стандарт MRZ документа (ICAO 9303 або «немає»).

## Поточний стан
- CRUD довідника: `/admin/document-types`, API `/api/v1/admin/document-types`, лише `ADMIN`.
- `field_definitions`: `key`, `nameUk`, `nameEn`, `nameRu`, **`required`**.
- `planned_scan_pages`: **JSON**-масив сторінок.
- `comment`: VARCHAR(512), у seed — MRZ-стандарт.
- Seed UA: 5 видів з UUID `c2000000-…0001`…`0005` (Flyway `V39`).
- Національний паспорт і ID-картка — **два різні види**.

## Scope
- Прапорець `required` у JSON поля, у API, у формі адмінки (крок «Поля документа»).
- Заміна `planned_scan_pages`: INT → JSON-масив сторінок.
- Колонка `comment` (VARCHAR) на виді документа; seed з MRZ-стандартом.
- Деструктивна міграція: `DELETE` усіх рядків `document_types`.
- Seed п’яти видів UA (див. каталог нижче).
- Тести CRUD і seed з новим полем і новим форматом сторінок.

## Поза scope
- Прив’язка до карток ТЗ / водіїв, OCR, сканів, класифікації документа.
- Інші країни, ІПН, CMR, TTN, страховки, договори.
- Автозапис значень у картки без підтвердження користувачем.
- Визначення `required` у рантаймі за regex чи контрольними сумами (тут лише прапорець у довіднику).

## Сенс `required`

| `required` | Поведінка |
|------------|-----------|
| `true` | Поле використовує система. Користувач підтверджує значення. Порожнє — відхилити. |
| `false` | Довідкове поле. Можна лишити порожнім. Система його не вимагає. |

Правила:
- Прапорець живе **на полі**, не на виді документа.
- У seed кожне поле має явне `true` або `false`.
- У формі адмінки новий рядок поля: `required = true` (за замовчуванням це системне поле).
- Якщо в старому JSON ключа немає — читати як `false` (захист парсера; після міграції всі рядки нові).
- Унікальність `key` всередині одного виду — як зараз.
- Список полів виду не може бути порожнім. Хоча б одне поле з `required: true`.

Підтвердження користувачем у цій спекі означає: значення обов’язкового поля потрапляє в систему лише після явної дії людини (збереження форми). Автопідстановка без submit заборонена.

## Модель поля (`field_definitions[]`)

```json
{
  "key": "passportNumber",
  "nameUk": "Номер паспорта",
  "nameEn": "Passport number",
  "nameRu": "Номер паспорта",
  "required": true
}
```

| Атрибут | Тип | Обов’язковий у JSON | Опис |
|---------|-----|---------------------|------|
| `key` | string, max 64 | так | `[a-zA-Z][a-zA-Z0-9_]*` |
| `nameUk`, `nameEn`, `nameRu` | string, max 128 | так | Підпис у UI |
| `required` | boolean | так | Системне поле + підтвердження |

Колонки виду документа: `id`, `name_*`, `country_code`, `planned_scan_pages` (JSON), `field_definitions`, `comment`, soft delete.

### `comment`

| | |
|---|---|
| **Колонка** | `comment` VARCHAR(512) NOT NULL DEFAULT `''` |
| **API** | `comment` string, max 512; порожній рядок дозволений |
| **Призначення** | Службова примітка до виду. У seed UA — **стандарт MRZ** (ICAO 9303 TD1 / TD3) або явна відсутність MRZ |

Це не локалізоване поле (коди ICAO лишаються латиницею). Не плутати з `required` на полях документа.

Усі п’ять seed-записів: `country_code = UA`, `is_deleted = false`.

## Модель сторінок скана (`planned_scan_pages`)

Колонка зберігає JSON-масив. Порядок елементів = порядок сторінок.

```json
[
  {
    "key": "1",
    "legendEn": "front",
    "legendUa": "лицьова сторона",
    "legendRu": "лицевая сторона"
  },
  {
    "key": "2",
    "legendEn": "back",
    "legendUa": "зворотна сторона",
    "legendRu": "обратная сторона"
  }
]
```

| Атрибут | Тип | Обов’язковий | Опис |
|---------|-----|--------------|------|
| `key` | string, max 32 | так | Ідентифікатор сторінки всередині виду; унікальний у масиві. У seed — `"1"`, `"2"` |
| `legendEn` | string, max 128 | так | Підпис сторінки (en) |
| `legendUa` | string, max 128 | так | Підпис сторінки (ua) |
| `legendRu` | string, max 128 | так | Підпис сторінки (ru) |

Правила:
- Порожній масив `[]` дозволений (сторінки скана не задані).
- `key` унікальні без урахування регістру всередині одного виду.
- Число сторінок = `planned_scan_pages.length`. Окремого INT більше немає.
- У seed чотирьох видів (ID-картка, закордонний паспорт, посвідчення водія, свідоцтво про реєстрацію ТЗ) — масив з двох сторінок (лицьова / зворотна), як у прикладі вище.
- У seed національного паспорта (книжка) — порожній масив `[]`.

## API

Контракт поля (create/update і відповідь):

```json
{
  "key": "licenseNumber",
  "nameUk": "Номер посвідчення",
  "nameEn": "License number",
  "nameRu": "Номер удостоверения",
  "required": true
}
```

- `required` — обов’язковий boolean, не `null`.
- `plannedScanPages` — масив об’єктів `{ key, legendEn, legendUa, legendRu }`, не число.
- `comment` — рядок, max 512; порожній дозволений. У seed — MRZ-стандарт з каталогу.
- Валідація виду: `fieldDefinitions` не порожній; є щонайменше один елемент з `required: true`; `key` полів унікальні без урахування регістру; `key` сторінок унікальні без урахування регістру; усі легенди сторінки не порожні.
- Коди помилок існуючого CRUD не ламати. Нові:
  - `DOCUMENT_TYPE_FIELDS_EMPTY` — порожній список полів;
  - `DOCUMENT_TYPE_NO_REQUIRED_FIELD` — немає жодного `required: true`;
  - `DOCUMENT_TYPE_SCAN_PAGE_KEY_DUPLICATE` — повтор `key` у `plannedScanPages`.

RBAC без змін: лише `ADMIN`.

## UI (`/admin/document-types`)

Крок «Опис документа»:
- Поле **Коментар** (`mat-form-field` + `textarea`): `comment`. Підказка: стандарт MRZ або службова примітка.
- Замість числа сторінок — список сторінок скана (`FormArray`): `key`, `legendUa`, `legendEn`, `legendRu`.
- Кнопка додати/видалити сторінку. Порядок у списку = порядок сторінок.
- У seed ID-картки, закордону, прав і свідоцтва ТЗ — два рядки: `1` / лицьова, `2` / зворотна.
- У seed національного паспорта (книжка) — порожній список сторінок.

Крок «Поля документа»:
- У рядку поля — `mat-checkbox` (або `mat-slide-toggle`) **«Обов’язкове»**, прив’язаний до `required`.
- Підказка: обов’язкові поля система використовує; користувач їх підтверджує.
- Список/картки: показувати «обов’язкових / усіх» (наприклад `6 / 8`), не лише кількість полів; `comment` — у картці/рядку (скорочений текст + tooltip).
- i18n: uk / en / ru.

Видалені записи (soft delete) — як зараз, поля тільки для перегляду.

## Міграція

Наступний вільний Flyway після поточних (`V38` уже зайнятий) — окремий скрипт, наприклад `V39__reset_document_types_ua_default_catalog.sql`.

Кроки в одній транзакції Flyway:

1. `DELETE FROM document_types;` — усі рядки, включно з soft-deleted.
2. Змінити колонку `planned_scan_pages`: INT → JSON.
3. Додати колонку `comment VARCHAR(512) NOT NULL DEFAULT ''`.
4. `INSERT` п’яти записів з UUID, `field_definitions`, `planned_scan_pages` і `comment`.
5. Кирилицю в SQL задавати через `CONVERT(UNHEX(...) USING utf8mb4)`, щоб на Windows seed не зіпсував кодування.
6. Таблицю не `DROP`. `required` — лише всередині `field_definitions`. `comment` — окрема колонка VARCHAR, не JSON.

Порядок `DELETE` перед `ALTER` теж допустимий: порожня таблиця, потім зміна типу, потім `INSERT`.

Це **деструктивна** зміна довідника. На цьому етапі на `document_types.id` немає зовнішніх ключів з інших таблиць. Якщо з’являться — міграцію не накатувати, поки FK не знімуть або не мігрують дані.

Ідемпотентність: повторний прогін Flyway не передбачений (версія вже застосована). Повторне заповнення — лише нова міграція.

## Бекенд / фронтенд (зміни коду)

Реалізовано:

- Record поля: `boolean required`.
- Entity/DTO: поле `comment` (string, max 512, порожнє дозволене).
- `planned_scan_pages`: тип JSON, record сторінки `{ key, legendEn, legendUa, legendRu }`; API-поле `plannedScanPages` — масив, не `int`.
- Request/DTO: `@NotNull Boolean required`; сторінки — `@Valid` список.
- Конвертер JSON полів: читати `required`; відсутній ключ → `false`.
- Сервіс: перевірка «є хоча б одне required»; унікальність `key` сторінок.
- Форма: контрол `required` у полях; `FormArray` сторінок замість числа; `textarea` для `comment`.
- Інтеграційні тести CRUD оновлені; seed-каталог перевіряється через репозиторій (у test-профілі Flyway вимкнено).

## Тест-план

- Unit: парсер `field_definitions` — з `required`, без ключа → `false`.
- Unit: парсер `planned_scan_pages` — масив сторінок; відмова на INT.
- Integration: DELETE+seed (через міграцію на тестовій БД) → GET list = 5, перевірка ключів, прапорців, сторінок і `comment` для кожного `id`.
- Integration: CRUD з `required`; відмова на порожній список полів і на список без обов’язкових полів.
- Manual: відкрити `/admin/document-types`; книжковий паспорт без сторінок скана; інші чотири — front/back; крок полів; UTF-8 ua/ru.

## Ризики

- Локальні/стейдж бази втратять ручні види документів — це навмисно.
- Зміна UUID свідоцтва про реєстрацію зламає будь-яке зовнішнє збереження старого `c1000000-…0001`. На момент спеки таких зв’язків у БД немає.
- Дублювання `key` між різними видами (`lastName`, `issuedOn`) — нормально; унікальність лише всередині одного виду.
